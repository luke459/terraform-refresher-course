# Build modules that are easy to use

Let's turn a small app tier into a reusable module. The key is deciding what the module accepts and returns, so callers don't need to know its internal resource layout.

## 2023 vs 2026

| Familiar pattern | What to practise |
| --- | --- |
| Split a large root into files | Use a child module when you need a separate scope |
| Reach directly for an internal resource | Pass inputs and read published outputs |
| Pin providers | Pin module sources using the right version mechanism too |

**3-Year Catch-Up:** Module scope and instance addresses still work the same way. We'll combine them with typed inputs and stable `for_each` keys, so reorganizing your code doesn't accidentally change resource identity.

<a id="sources" />
## Pick a source and know how to install it

A module source can be a local directory such as `./modules/app-tier`, a public or private registry address, or a supported package location such as Git or S3. Run `init` after changing the module's source configuration. Include `./` for a local relative path so it isn't mistaken for a registry address.

```hcl
module "app_tier" {
  source      = "./modules/app-tier"
  for_each    = var.environments
  network     = each.value
  environment = each.key
  attempt_id  = var.attempt_id
}
```

Terraform resolves the source during initialization; it isn't an arbitrary runtime expression. Read remote module code and pin the package you intend to use. A familiar provider namespace doesn't tell you whether a module fits your project.

<a id="scope" />
## Files share a module; child modules have their own scope

Ordinary `.tf` files in one directory form one module. Moving a variable between those files doesn't create a new scope. Calling a child directory as a module does.

A child can't use a root variable or local by name unless you pass it through a declared input. The root can't read `module.app_tier.aws_vpc.app.id` either. Instead, the child publishes an output such as `vpc_id`, and the root reads it. Try Scope Debugger to practise both directions.

<a id="composition" />
## Pass in what the module needs; return what callers need

The lab's network input contains a VPC CIDR and subnet CIDR. The child creates resources and returns selected IDs. Keep provider configuration in the root for this reusable pattern; the child declares its provider requirements and uses the supplied configuration.

Adding `for_each` creates a map of module instances. Read `module.app_tier["dev"].vpc_id` for one environment, or use a `for` expression to collect results from all of them. Resources below `module.app_tier["dev"]` have different addresses from those below stage. Keep the keys stable when the environments stay the same.

```hcl
value = jsonencode({
  for name, tier in module.app_tier : name => tier.vpc_id
})
```

These output references also give Terraform the dependencies it needs. You don't need to add a broad `depends_on` for every resource inside the child. Let the values describe the relationships where possible.

<a id="versions" />
## Pin module versions separately from providers

For registry modules, use the module's `version` argument with a suitable constraint. For Git sources, choose a ref such as `?ref=v1.2.0`. A branch can move; a commit identifies a specific revision. `.terraform.lock.hcl` locks providers, not module packages.

Review a new plan whenever you change a module source or version. Moving resources from a flat configuration into a child changes their addresses unless you declare the moves. This lab starts in a disposable workspace; domain 06 will show you how to refactor existing addresses while keeping their remote IDs.
