## A repeatable debugging method

Taking over an unfamiliar repository can feel like several problems at once. Start by learning how it runs, then tackle one failure at a time. Aim for a small fix you can explain and check.

Use this loop: **orient → reproduce → classify → isolate → repair → prove**. Before each check, write down what you expect. If the result doesn't fit your explanation, rethink it before editing another file.

<a id="orient" />
## 1. Orient: find your starting point

Read the README, CI workflow and Makefile. Check version files, `required_version`, `required_providers`, `.terraform.lock.hcl` and `.tflint.hcl`. Find the root modules, child modules, environment directories and variable files. Files in one module directory belong together; separate directories aren't automatically one configuration.

Note the commit or local diff, working directory, tool versions, account/region, backend, workspace and input files. Keep secrets out of your notes. Compare CI with your terminal: does it use a container, `-chdir`, a different workspace, injected variables or another role?

```sh
git status --short
git diff --stat
terraform version
tflint --version
```

Read unfamiliar scripts before running them. Initialization can contact registries and remote storage. This course uses Terraform 1.12.2; in another project, start with its supported versions. Save upgrades for a separate, reviewed change.

<a id="reproduce" />
## 2. Reproduce: capture one clear failure

Run the failing command in the right directory with CI's versions and non-secret inputs. Save the exit code and full diagnostic: file, line, resource address, module path and any request ID. Look for the first error that explains the later ones, rather than starting at the bottom of the log.

A short note helps you stay focused:

```text
Context: commit, root directory, environment, versions
Command: exact command and input-file names, without secrets
Expected: the behavior the project intends
Observed: diagnostic, location, exit status and relevant log excerpt
Hypothesis: one specific explanation
Experiment: the smallest check that could disprove it
Fix and proof: changed files, checks run, remaining uncertainty
```

Make your explanation specific enough to test. “Plan fails” doesn't tell you where to look. “The root asks for internal_id, but the child exports id” gives you two files to compare.

<a id="classify" />
## 3. Classify: work out which stage failed

| Stage | What you might see | Start here |
| --- | --- | --- |
| Parsing or formatting | Unclosed block, invalid expression, fmt differences | Check the cited syntax. Formatting alone doesn't prove the configuration is valid. |
| Initialization | Download, checksum, provider or backend error | Check versions, lockfile, platform, sources and backend access. |
| Configuration validation | Missing argument, unsupported attribute, wrong type, cycle | Trace the reference, its scope and the expected type. |
| Linting | A named TFLint rule fails | Match CI's linter and config, then read the rule. |
| Planning | Invalid input, unknown keys, replacement, failed condition | Check the inputs and the reason for each proposed action. |
| Apply or provider API | AccessDenied, quota, timeout, service error | Check identity, action, resource, region and anything already created. |
| Backend or state | Lock, stale plan, state-access or mapping error | Confirm the backend, workspace and run owner before recovery. |

Match the fix to the failure. Formatting won't grant an AWS permission, and disabling lint won't add a missing module output. Passing validation is useful, but API access and apply-time conditions still need their own checks.

<a id="static" />
## 4. Isolate: start with a small configuration check

Once you understand the environment, follow the project's normal initialization steps. For a separate copy used only to inspect configuration, you can skip backend setup and keep the locked provider version:

```sh
terraform fmt -check -recursive
terraform init -backend=false -input=false -lockfile=readonly
terraform validate -json
```

This doesn't read the remote managed state or prepare the copy for deployment. If readonly initialization fails, check the constraint, platform checksums and any mirror or proxy. Don't reach straight for `init -upgrade`, delete the lockfile or edit its hashes by hand. [Initialization](https://developer.hashicorp.com/terraform/cli/commands/init).

After installing modules and providers, validate checks syntax and internal consistency without querying live infrastructure. Its JSON gives severity, detail and source locations. Keep stderr and the exit code too: some failures happen before valid JSON is available. For a missing child output, compare the root reference with what the child exports. [Validation](https://developer.hashicorp.com/terraform/cli/commands/validate).

For a tricky expression, try a small, non-secret example in `terraform console`, such as `type(var.services)` or `keys(var.services)`. “Not known until apply” differs from “doesn't exist.” Give `for_each` known keys and put apply-time IDs in the values. Use a real plan to check blocking input conditions afterward.

### Check lint failures separately

Review the project's plugin sources, then initialize the pinned plugins and use CI's command. An absolute config path helps recursive checks use the intended settings:

```sh
tflint --init
tflint --recursive --config="$(pwd)/.tflint.hcl"
```

For `terraform_typed_variables`, add the right explicit type. For provider rules, check the schema and provider version. If local and CI results differ, compare TFLint and plugin versions, rules, working directory and variables. Keep CI checks enabled. If an exception is justified, document the exact rule, scope and reason. [TFLint configuration](https://github.com/terraform-linters/tflint/blob/v0.57.0/docs/user-guide/config.md).

<a id="plan" />
## 5. Plan with the right environment and inputs

Confirm the backend, workspace and approved credential process before planning against an existing environment. Match the failing run's variable files. Check required values, types, nulls, defaults, validation and `TF_VAR_` overrides. Compare selected settings without printing whole environment or credential files.

For AWS, `aws sts get-caller-identity --profile PROFILE` checks the CLI identity. Provider aliases, `assume_role` and backend credentials may use different identities, so follow each connection. This course passes your selected AWS connection to the runner's tools; check that consistency yourself in other projects.

```sh
terraform plan -input=false -detailed-exitcode -out=reviewed.plan
terraform show -no-color reviewed.plan
```

Detailed exit codes mean **0** for no changes, **2** for changes and **1** for an error. Without the flag, exit 0 only means planning succeeded. Read the addresses and actions too. For a surprise replacement, compare arguments, immutable fields, module addresses and inputs. A moved block can handle an address change; it can't avoid replacing a genuinely changed immutable field. Keep saved plans and their JSON private. [Planning](https://developer.hashicorp.com/terraform/cli/commands/plan).

Avoid `-target` as a shortcut around a graph or type error: it can leave the problem outside the plan. `-refresh=false` can help compare an idea, but may use stale observations. Refresh-only records remote observations; it doesn't restore your HCL settings in AWS.

<a id="runtime" />
## 6. Follow the clues in technical failures

### Downloads, networking and provider schemas

First check whether the failure is a package download, backend access or resource API call. Look at the hostname, DNS, TLS, proxy settings and supported OS/CPU. For a plugin that won't start, check its executable, platform and runtime restrictions. For an unsupported argument, compare the locked provider's schema with the example: a newer tutorial may use a field your version doesn't have.

### AccessDenied, expired sessions and API errors

Find the denied action, resource, role/account and region. Check the relevant identity/resource policies, boundaries, organization controls and encryption-key permissions. A working login doesn't mean every action is allowed. Refresh expired SSO or temporary credentials, then confirm the original account before resuming.

An apply can fail after creating some resources. Read the log, state and live IDs before retrying. Fix the cause and make a fresh plan; the old saved plan may be stale. Use the service error and request ID for quota, input and dependency failures. Longer timeouts won't fix denied permissions. Retry temporary failures within a limit, checking whether the first attempt already succeeded.

### Locks, drift and state

Read the lock owner, operation, ID, creation time and state path. Check the matching CI job or operator run. Let an active owner finish, or cancel through its normal workflow. Use force-unlock only after confirming that the exact lock is stale; another writer may still need its protection. [Lock recovery](https://developer.hashicorp.com/terraform/cli/commands/force-unlock).

Inspect state to tell a wrong address or workspace from a missing import or deleted object. Keep pulled state private. `state rm` leaves the remote object running. For drift, compare HCL, state and AWS, then decide whether to keep the outside change or restore the configured setting. The course's cleanup inventory also checks objects that state has forgotten.

<a id="logs" />
## 7. Use focused logs when you need more detail

Start with the normal error. If it isn't enough, capture one reproduction with component logging. For an API problem, provider logs are usually easier to follow than a full core trace:

```sh
umask 077
TF_LOG_PROVIDER=DEBUG TF_LOG_PATH=./private-provider.log terraform plan
```

Choose a private, ignored path. Raw logs can contain credentials, secrets and request/response data, even when outputs are marked sensitive. These variable assignments apply to this command only. Return to normal logging afterward and remove captures you no longer need. Share reviewed excerpts with the command context, address and request ID. Use `TF_LOG_CORE` for graph or expression questions. [Logging](https://developer.hashicorp.com/terraform/internals/debugging).

<a id="repair" />
## 8. Make one fix and check it worked

Write your explanation in one sentence, test it, then make the smallest useful change. Keep unrelated upgrades, module changes and infrastructure replacements separate. Review the diff after formatting.

Rerun the original failing check, the relevant static checks and a fresh plan with the intended inputs. Explain any remaining changes. If deployment is approved, apply the reviewed plan, check the result and inspect the next plan. Some projects expect deferred reads or changes, so check against the intended result rather than treating every nonzero plan code as failure.

Finish with the cause, changed files, checks and anything unresolved. Add a regression check if it would catch this failure again. Make sure you tested the original root, workspace, versions and inputs.

### Worked example: four failures, one at a time

In the practice repository, fmt first reports a formatting issue. After fixing it and initializing, validate finds `module.service.internal_id`, but the child exports `id`. Fix that reference, and lint then asks for an explicit variable type. Finally, planning rejects the default `replicas = 0` because it must be a positive integer.

Change the reference, add `type = number`, and choose a valid replica count. Rerun the checks, apply the local fixture and check that the next plan has no changes. The Repository workshop has the runnable project and reference repair. It uses only `terraform_data`, so you don't need AWS credentials and won't create cloud resources.
