## Investigate an inherited repository

Allow 30–45 minutes. You'll fix a small project that uses Terraform's built-in `terraform_data` resource. It requires no AWS access or external provider download; apply and destroy only affect this disposable local fixture.

### Start with your own copy

From the host repository, open a shell in the course container and copy the broken project into a new workspace:

```sh
docker compose exec course sh
practice_dir=$(mktemp -d /workspaces/debugging.XXXXXX)
cp -R /app/curriculum/troubleshooting/repository/. "$practice_dir/"
cd "$practice_dir"
```

You can also find the files at `curriculum/troubleshooting/repository` on the host. Open your copy in an editor. Save the reference repair at `curriculum/troubleshooting/solution` for comparison after you've tried a diagnosis; in the container, use `/app/curriculum/troubleshooting/solution`.

### Your investigation

For each failure, note the error, where it happened, your explanation and a check to test it. Run these commands one at a time so you can read each result:

```sh
terraform version
tflint --version
terraform fmt -check -recursive
terraform init -backend=false -input=false
terraform validate -json
tflint --recursive --config="$(pwd)/.tflint.hcl"
terraform plan -input=false -detailed-exitcode -out=reviewed.plan
```

1. Find the formatting difference, run `terraform fmt -recursive`, and review the changed file.
2. Follow the unsupported attribute from the root output to the child's outputs. Fix the caller to use the output the child actually exports.
3. Compare validate and lint. The default value lets Terraform infer a type, but the lint rule asks you to declare it explicitly. Add the right type.
4. Read the input error from Plan. Choose a positive whole-number default or supply a valid input. The reference uses `replicas = 2` as the default.
5. Rerun fmt check, validate and recursive lint. Review the plan: it should create one local `terraform_data` object and no AWS resources. Detailed exit code 2 is expected before the first apply.
6. Apply your reviewed plan, then check for detailed exit code 0 on the next plan:

```sh
terraform apply -input=false reviewed.plan
terraform plan -input=false -detailed-exitcode
terraform destroy -input=false -auto-approve
terraform state list
```

The auto-approved destroy is for this disposable local fixture. Follow the project's approval process for a real cloud environment. Check that state is empty, then keep your notes and source diff.

### Explain what you fixed

A useful handoff could say:

“The root referenced an output the child didn't export. I switched it to `module.service.id`, declared the replica input as a number and changed its invalid default to 2. Format, validate and lint pass. The plan creates one local object; after apply, the next plan has no changes. I destroyed the fixture. No AWS resources or credentials were used.”

To see the same sequence checked automatically, run `make check-troubleshooting` from the host. Or use the container's installed tools with `docker compose exec course python scripts/check_troubleshooting.py`. It tests the failures and repairs in a temporary directory, applies and destroys the local fixture, and writes a report under `docs/evidence` where you ran it.
