# Work with state, locks and drift

State connects your Terraform addresses to real resources. Let's practise moving it, handling locks, and refactoring addresses while keeping track of what still exists in AWS.

## 2023 vs 2026

| Familiar pattern | What to practise |
| --- | --- |
| S3 state with a DynamoDB lock table | Native S3 lockfiles and their permissions |
| Rename a resource, then repair state | Review a declared move before applying |
| Reach for refresh after a console edit | Decide whether to accept or undo the outside change |

**3-Year Catch-Up:** S3 supports `use_lockfile = true`, and DynamoDB locking is deprecated. Keep practising moved blocks and refresh-only mode too. A removed block adds a way to stop managing an object without destroying it.

<a id="local" />
## Start with the backend you have

The local backend normally keeps state on your filesystem. It differs from a shared remote backend, but its state still links addresses to remote objects and can hold secrets. Keep it out of Git and back it up before changing mappings. Use the state commands rather than editing JSON by hand.

The lab creates its state bucket from a separate bootstrap directory with local state. That bucket must exist before the workload can use it as a backend. Keep the two states separate, and destroy the bootstrap resources last.

<a id="locking" />
## Let one writer finish at a time

```hcl
terraform {
  backend "s3" {
    use_lockfile = true
    encrypt      = true
  }
}
```

Native S3 locking uses a separate key ending in `.tflock`. It needs read, write and delete permissions for that lock object as well as the appropriate state permissions. Encryption, locking and versioning solve different problems; enabling one doesn't replace the others.

If another operation owns the lock, check that run before trying to remove it. The Lock Contention Lab lets you practise locally. The AWS lab's probe creates its own test lock, checks that Terraform reports contention, then removes only that probe's matching lock ID.

<a id="remote" />
## Move state with the backend migration workflow

Use partial backend configuration for settings such as bucket, key and region. Keep credentials in the selected AWS connection, outside the checked-in backend file. Backend configuration can't reference ordinary root input variables as a resource argument would.

Use `init -migrate-state` to move existing state. `-reconfigure` instead forgets the current backend configuration association without requesting migration. The lab checks the owned bucket identity before migrating. Keep the backend available until you've destroyed the resources whose state it holds.

`terraform_remote_state` exposes another state's root outputs, but the reader still needs access to the underlying snapshot. That snapshot can contain much more than the outputs. If a consumer only needs one value, consider sharing it through SSM rather than giving it state access.

<a id="drift" />
## Decide what should change: state, configuration or AWS

A refresh-only apply records what it finds remotely in state and outputs. It doesn't edit HCL or restore a changed parameter. A later normal plan can still propose restoring the configured value. You'll see this in the lab after changing an SSM value and tag outside Terraform.

```hcl
moved {
  from = aws_ssm_parameter.legacy
  to   = aws_ssm_parameter.metadata
}
removed {
  from = aws_ssm_parameter.detached
  lifecycle {
    destroy = false
  }
}
```

The moved block changes the Terraform address while preserving the remote object. The removed block shown here forgets the object without deleting it. That detached object remains part of your lab's cleanup inventory, even though it no longer appears in state.

To finish, destroy the workload while its backend exists, migrate the empty state back to local, and clean up the detached object. Then remove the versioned backend bucket, including saved versions, and verify that all owned resources are gone.
