# Get comfortable with the Terraform workflow

Let's walk through the commands you'll use most often, and what each one can tell you before you change anything in AWS.

## 2023 vs 2026

| Older muscle memory | Try in this course |
| --- | --- |
| Mark an object tainted before apply | Review a plan that includes `-replace` |
| Run refresh out of habit | Choose a normal or refresh-only operation for the task |
| Read a successful plan as “no changes” | Check the detailed exit code and proposed actions |

**3-Year Catch-Up:** Some of these commands predate 2023. The useful practice is putting them together: initialize, validate, save and review a plan, apply it, check the result, then clean up.

<a id="workflow" />
## Write, plan, apply

Write the system you want in HCL. Plan to compare it with the current environment, then apply the reviewed changes. A successful apply doesn't prove your application works. If apply stops halfway through, keep the workspace and inspect state: some resources may already exist.

<a id="init" />
## Initialize the working directory

Run `terraform init` in a new working directory and after relevant backend, module or provider changes. It sets up backend access and installs modules and providers. If you're moving state, use the migration workflow; `init -reconfigure` doesn't migrate it for you.

The course normally initializes against committed provider lockfiles in readonly mode. Use the provider-locking command when adding platform checksums, so you can review the change separately from a dependency upgrade.

<a id="validate" />
## Catch configuration errors early

`terraform validate` checks syntax and internal consistency using installed modules and provider schemas. It's a useful first check before an AWS apply. It can't confirm that a bucket name is available or that your IAM role has permission to create it.

Planning adds real input values and provider behaviour. The lab's invalid subnet CIDR gives you a chance to see which checks catch the problem and when.

<a id="plan" />
## Read the plan before applying

```sh
terraform plan -detailed-exitcode -out=tfplan
terraform show tfplan
terraform apply tfplan
```

A saved plan records the proposed changes. Keep it private—it may contain sensitive data—and generate a new one after editing configuration. The runner checks the saved plan's hash and rejects one that has changed or become stale. A binary file isn't automatically encrypted.

With detailed exit codes, **0** means no changes, **1** means an error, and **2** means changes are proposed. A normal plan refreshes relevant tracked objects. `-refresh=false` skips that check and can miss recent remote changes. `-refresh-only` plans updates to state and outputs without making infrastructure match your HCL.

Save `-target` for exceptional recovery work, then review a full plan afterward. It can leave changes elsewhere in the graph out of view.

<a id="apply" />
## Put replacement in the plan

```sh
terraform plan -replace=aws_security_group.app -out=tfplan
terraform apply tfplan
```

A replacement creates a new remote object with a new identity. A `moved` block does something different: it changes the Terraform address while keeping the existing object. In the lab, capture the old security group ID so you can check that replacement really happened.

<a id="destroy" />
## Clean up the right resources

`terraform destroy` works on managed objects in the selected state. Check the account and backend first. It won't discover setup resources that were never imported, or objects you removed from state. The course keeps an inventory of those owned IDs so cleanup can check them too.

<a id="fmt" />
## Keep formatting separate from validation

Use `terraform fmt -recursive` to format files, or `terraform fmt -check -recursive` to report differences in CI. Formatting doesn't test AWS permissions. Run it before reviewing your plan so the files you save and the plan you apply stay in sync.
