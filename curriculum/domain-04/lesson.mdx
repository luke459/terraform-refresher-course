# Write configuration that's easier to trust

Let's make your inputs clearer, your dependencies easier to follow, and your secrets less likely to end up in saved files.

## 2023 vs 2026

| Familiar feature | What to practise |
| --- | --- |
| Variable validation and lifecycle rules | Conditions, dependencies and unknown values |
| Sensitive values hidden in output | Ephemeral values and write-only provider arguments |
| Index-based repetition | Stable keys when names identify your resources |

**3-Year Catch-Up:** Preconditions and postconditions arrived in 1.2, checks in 1.5, ephemeral values in 1.10, and write-only arguments in 1.11. The course's Terraform 1.12.2 supports them, but your provider must support the resource feature too.

<a id="resources-data" />
## Manage an object or read information about it

Use a `resource` block for an object Terraform manages, and a `data` block to read provider information. Reading a bucket doesn't make Terraform responsible for deleting it. Some attributes stay unknown during planning because the operation that produces them hasn't happened yet.

<a id="references" />
## Let references carry dependencies

`vpc_id = aws_vpc.course.id` supplies a value and tells Terraform which resource must come first. Pasting the same ID as a string doesn't create that dependency. Prefer the reference when one resource needs a value from another.

<a id="inputs-outputs" />
## Give callers clear inputs and outputs

Input variables accept values, locals name intermediate expressions, and outputs share selected results. Choose useful types and validation. For CLI runs, command-line variable settings override automatic variable files and environment variables. Check where a value comes from when a plan surprises you.

A sensitive output still goes into state. An ephemeral child-module output can pass a temporary value to a compatible ephemeral context, but a root output can't simply publish it as a persistent result.

<a id="types" />
## Choose how a collection identifies its items

| Type | What to remember |
| --- | --- |
| list | Ordered elements with one element type |
| set | Unique elements without positional identity |
| map | String keys with one element type |
| object | Named attributes, each with its own type |
| tuple | Fixed ordered positions, each with its own type |

A `map(object({ port = number, cidr = string }))` is useful for named services. With `for_each`, each map key becomes part of the resource address. With `count`, removing a middle list item can shift the items at later indexes. Choose stable keys when you want names to preserve identity. Those keys must be known during planning and can't be sensitive.

<a id="expressions" />
## Transform values with expressions

Use `for` to transform collections and a conditional expression to choose a value. Functions such as `jsonencode`, `merge`, `lookup`, `toset`, `length`, `can` and `try` help with common operations. `dynamic` generates nested blocks; it doesn't create resource instances or meta-argument blocks.

```hcl
validation {
  condition = alltrue([
    for service in values(var.services) :
    service.port >= 1 && service.port <= 65535 && can(cidrhost(service.cidr, 0))
  ])
  error_message = "Use valid CIDRs and ports in 1..65535."
}
```

<a id="dependencies" />
## Choose lifecycle rules for the job

Use `depends_on` for a real dependency that value references can't express. Broad dependencies can make more values unknown during planning.

`create_before_destroy` changes replacement order, so names and quotas must allow both objects to exist together. `prevent_destroy` blocks planned destruction while the rule applies; removing the resource declaration removes that protection. `ignore_changes` hands selected updates to another system while Terraform still manages the object.

<a id="conditions" />
## Know which checks stop an operation

Input validation rejects invalid arguments. Preconditions test assumptions before the relevant operation; postconditions check results after planning, applying or reading data. Known values can be checked during planning. Unknown values may defer the check until apply, when a blocking failure can stop the operation or its dependents.

A failed top-level `check` assertion produces a warning rather than blocking the operation. The lab still requires its checks to pass before awarding credit. Try the Evaluation Order Visualizer to see when values become available.

Watch for this lab's planning detail: a scoped check data source can need another read even when no managed resources or root outputs change. On the pinned runtime, that can produce detailed exit code 2. This grader checks the saved plan's actual resource and output changes; the simpler labs require exit code 0.

<a id="secrets" />
## Hiding a value doesn't remove it from state

`sensitive = true` hides values in many normal outputs, but they can still appear in state and saved plans. Ephemeral values are omitted from those files and can only flow into compatible contexts.

For the AWS secret version, pass an ephemeral password through `secret_string_wo`. Increment the non-secret `secret_string_wo_version` counter when you want an update: Terraform can't compare the old write-only password.

Vault can supply secrets, including short-lived credentials, but the downstream fields still decide whether they persist. Follow the value through its inputs, provider fields, outputs and logs. You don't need a Vault server for this lesson.

The lab compares the actual secret with state, plan data and saved workspace files without printing it. A null write-only field alone wouldn't catch a copy saved elsewhere.
