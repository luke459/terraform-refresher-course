# Bring existing resources into Terraform

Let's import resources without replacing them, then use state commands and focused logs to understand what Terraform did.

## 2023 vs 2026

| Older workflow | What to practise |
| --- | --- |
| Run CLI import, then write HCL | Review import blocks and refine generated configuration |
| Use state commands as quick fixes | Check what changes in state and what stays in AWS |
| Turn up logging and share the capture | Capture what you need and keep raw logs private |

**3-Year Catch-Up:** Import blocks let you review adoption through the usual plan/apply workflow. Generated HCL gives you a starting point. You'll still need to check the arguments and decide which settings belong in your configuration.

<a id="import" />
## Match an address to an existing object

```hcl
import {
  to = aws_s3_bucket.imported
  id = "the-existing-bucket-name"
}
```

`to` chooses the Terraform resource address. The provider defines the import ID format: an S3 bucket uses its name, while an IAM policy uses an ARN. Check the resource's import documentation rather than assuming every AWS ID is an ARN.

Adding an ordinary resource block doesn't automatically adopt a same-named object. An import block lets Terraform plan that connection and apply it. The older `terraform import ADDRESS ID` command also connects an object to state, but doesn't write the resource configuration you'll need afterward.

If the resource configuration doesn't exist yet, try `terraform plan -generate-config-out=generated.tf`. Review the file for conflicting, unsupported or unnecessary default arguments. Even a failed plan can leave useful generated HCL. When comparing it with the reference, keep only one declaration for each address.

Check the bucket name and policy ARN before and after import, look for replacements, and finish with a no-change plan. The setup action records the objects before import, so a failed import doesn't lose them from the cleanup inventory.

<a id="state-cli" />
## Inspect state before changing it

| Command | What it does |
| --- | --- |
| `state list` | Lists tracked addresses |
| `state show ADDRESS` | Shows one tracked object's attributes |
| `state pull` | Reads the raw state snapshot |
| `state mv OLD NEW` | Changes an address mapping while keeping the cloud object |
| `state rm ADDRESS` | Forgets an association while leaving the object running |

Practise moves and removals with disposable resources. Back up state and check the account, backend and next plan. If you forget an object but leave its resource declaration, Terraform can try to create another one. Prefer moved or removed blocks for refactors you want teammates to review.

<a id="logging" />
## Find useful details without sharing secrets

`TF_LOG` supports TRACE, DEBUG, INFO, WARN and ERROR. Use `TF_LOG_CORE` or `TF_LOG_PROVIDER` to focus on one component. `TF_LOG_PATH` sets the destination; it doesn't set a logging level.

```sh
TF_LOG_PROVIDER=DEBUG TF_LOG_PATH=tf-debug.log terraform plan
```

Provider logs can contain request or response data, including secrets hidden in normal output. Inspect captures locally, restrict access and remove them when you're done. Log Triage uses a made-up AccessDenied example so you can practise without credentials or API calls.

If you see AccessDenied, start with the active identity and required permission. Re-test the connection before changing HCL to work around an authentication problem. The course uses your explicitly selected profile or keys, so it won't silently switch accounts.
