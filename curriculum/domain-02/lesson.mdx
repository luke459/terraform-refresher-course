# Get comfortable with providers and state

Let's connect three pieces: the provider version you install, the AWS region each resource uses, and the state that tracks the result.

## 2023 vs 2026

| Familiar habit | Try in this course |
| --- | --- |
| Set a provider constraint and run init | Commit the selected version and checksums too |
| Set one AWS region in the environment | Choose a provider configuration for each region |
| Think of state as a cache | Use state to track resource addresses and AWS IDs |

**3-Year Catch-Up:** Aliases and lockfiles may already be familiar. We'll use them across Apple Silicon and both Linux container architectures. Remember: a Linux container on your Mac still needs Linux provider packages.

<a id="versions" />
## Constraints choose a range; lockfiles record a version

Put provider sources and version constraints in `required_providers`. Use a `provider` block for settings such as region. Terraform itself has a separate `required_version` constraint.

```hcl
terraform {
  required_version = "= 1.12.2"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.80"
    }
  }
}
```

The extra version component matters: `~> 5.80` allows 5.x releases from 5.80 onward, while `~> 5.80.0` stays below 5.81.0. Commas mean AND: `>= 5.0, < 6.0, != 5.81.0` allows the range but excludes one release.

A normal `init` reuses a compatible version from `.terraform.lock.hcl`. Use `init -upgrade` when you intend to consider newer allowed versions. Commit the lockfile, but keep `.terraform/` out of Git. The lockfile records provider versions and package checksums; it doesn't lock module versions or store AWS credentials.

To prepare the supported platforms, run `terraform providers lock -platform=linux_amd64 -platform=linux_arm64 -platform=darwin_arm64`. Keep the command result and test readonly initialization on each platform. The hashes don't contain platform labels. If a checksum fails, investigate the package and platform before changing the lockfile.

<a id="architecture" />
## Providers are plugins

Terraform core reads your configuration, builds the dependency graph and coordinates state. Providers supply resource and data-source schemas and talk to their APIs. Installing Terraform alone doesn't install every provider; `init` installs the ones your configuration and modules need.

Check both versions when a feature isn't available. Terraform 1.12 supports write-only arguments, but the provider must expose the field too. That's why this course pins AWS 5.92.0 and random 3.7.2.

<a id="aliases" />
## Choose the provider configuration explicitly

```hcl
provider "aws" {
  region = "us-east-1"
}
provider "aws" {
  alias  = "uk"
  region = "eu-west-2"
}
resource "aws_ssm_parameter" "uk" {
  provider = aws.uk
  name     = "/course/region"
  type     = "String"
  value    = "eu-west-2"
}
```

Here, `provider = aws.uk` sends the resource to London. Calling a resource `uk` doesn't choose a provider for it. If every provider block has an alias, a resource without a provider selection may still try to use an implied default configuration.

Child modules can inherit provider configurations. Aliases need the appropriate explicit mappings and declarations. Check those connections when a resource appears in the wrong region.

<a id="state" />
## Addresses are not cloud IDs

`aws_ssm_parameter.uk` is Terraform's resource address; `/course/region` is this parameter's AWS identifier. State links the two and records attributes and dependency information needed for later operations. Removing the address from state doesn't delete the AWS parameter.

Two parameters can share a name when they're in different regions. In the lab, you'll check each region's value and ownership tags separately. Keep state private even when these example values look harmless: real state can contain sensitive data.
