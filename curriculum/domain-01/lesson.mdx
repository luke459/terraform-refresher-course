# Infrastructure as code, revisited

Let's start with the idea you probably remember: tell Terraform what you want, review the changes, then apply them. Configuration describes your goal; state links that configuration to the objects Terraform manages.

## What Terraform declares

A shell command says “create a bucket now.” A resource block says “this bucket should exist with these settings.” State connects an address such as `aws_s3_bucket.course` to its AWS object. On the next run, Terraform checks the relevant remote information and plans any differences.

```hcl
resource "aws_s3_bucket" "course" {
  bucket = "an-account-specific-course-name"
}

resource "aws_s3_bucket_versioning" "course" {
  bucket = aws_s3_bucket.course.id
  versioning_configuration {
    status = "Enabled"
  }
}
```

Notice the bucket reference in the versioning resource. That creates the dependency; file order doesn't decide which resource comes first. The versioning block configures the same bucket, rather than creating another one.

A matching name isn't enough to bring an existing bucket under Terraform management. You'll need an import, which we'll cover in domain 07. For now, read the supplied script without running it, so Terraform can create and track the lab resources itself.

Here's the script's creation sequence for comparison:

```sh
aws s3api create-bucket --bucket "$COURSE_BUCKET" --region us-east-1
aws s3api put-bucket-versioning --bucket "$COURSE_BUCKET" \
  --versioning-configuration Status=Enabled
aws ssm put-parameter --name "$COURSE_PARAMETER" --type String \
  --value '{"environment":"refresher","project":"tf-004-prep"}'
```

## Check that the next plan has no changes

Keeping configuration in Git helps you review and repeat changes. You still need to check the account, pin your tools, and read each plan. A successful apply can include a replacement you didn't intend.

After applying, run `terraform plan -detailed-exitcode`. Read the result like this:

- **0:** no changes are proposed.
- **2:** changes are proposed.
- **1:** planning failed.

Without that flag, exit code 0 only tells you that planning succeeded. It doesn't tell you whether the plan is empty. When the next plan has no changes, you've checked that Terraform has reached the desired state—this is the idempotency check.

The action symbols tell you what will happen:

- `+` creates an object.
- `-` destroys an object.
- `~` updates it in place.
- `-/+` replaces it, destroying first; `+/-` creates first.

Suppose someone disables bucket versioning in the console. A normal plan should propose restoring the setting in your HCL. A refresh-only apply instead records what it finds in state; it doesn't repair the bucket or edit your configuration.

## Tell multi-cloud, multi-tier and hybrid apart

One configuration can use AWS, another cloud, and a DNS or monitoring service. Each provider handles its own API. Two AWS regions still use one cloud provider, so that alone isn't multi-cloud.

Multi-tier describes application layers: web, application and database tiers can all run in AWS. Hybrid combines private or on-premises infrastructure with a public cloud. The plan/apply workflow works across these services, but their resource schemas and permissions still differ.

Try Architecture Triage to sort the examples. Then use the Idempotency Simulator to predict the next plan after a console edit. You'll use AWS in the labs, but these ideas apply beyond AWS.

## Apply, verify, and clean up

Your lab replaces the script with a versioned bucket and an SSM parameter. Keep the supplied tags and unique names. Use the terminal to initialize, format, validate, save and apply a plan. Make another saved plan with detailed exit codes, then run `lab grade`.

Passing the lab checks earns **50%**. Destroy the resources and run `lab check-cleanup` to reach **100%**. Empty state alone isn't enough: a resource removed from state can still exist in AWS. The course checks the resource IDs recorded for your attempt.
